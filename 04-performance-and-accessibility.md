# 04: Performance and accessibility

Measured on the Mythical Pickles site. Tools: Lighthouse (mobile profile, simulated slow phone) against a local server, plus real-Chrome paint timing (`reference/tools/perf.mjs`).

## Where it ended up

| Measure | Result |
|---|---|
| Lighthouse accessibility | **100** on every page tested |
| Lighthouse best practices | **100** |
| Lighthouse performance | Oracle 97, flavor pages 85, home about 62 (the WebGL hero) |
| Real Chrome, first visit (intro plays) | first paint about 0.6 s |
| Real Chrome, repeat visit | first paint about 0.16 s |
| Layout shift (CLS) | 0 |
| Page code | CSS 9 KB and JS 11 KB after compression; biggest image 307 KB; 103 files, 9.5 MB total |
| Third-party requests on load | none (fonts and libraries are self-hosted) |

Lighthouse's SEO score shows 66 on a draft because the site deliberately says "noindex" until launch. Ignore it in drafts.

## What actually moved the numbers

1. **Remove the animation library from the critical path.** GSAP + ScrollTrigger were about 115 KB of JavaScript on every page. Only the motion-kit pieces need GSAP. We rewrote the intro (Web Animations API), the scroll effects (one shared, frame-throttled scroll handler) and the parallax in small native code, and load GSAP only when the Oracle or a legend film starts.
2. **Do not eager-load images below the fold.** Three product cards were loading with `loading="eager"` on the home page and competed with the hero image (about 540 KB). Only the very first screen's image should be eager or `fetchpriority="high"`.
3. **Give the LCP image its final position in CSS, not JavaScript.** The hero image was moved by a script after load, which caused a layout shift (CLS 0.14) and delayed the first paint. Reimplementing the same maths in CSS (`min()`, `max()`, `calc()` with custom properties) fixed both, and `reference/tools/geomcheck.mjs` proves the CSS matches the script to the pixel.
4. **Responsive images with real `srcset` and `sizes`**, in WebP, generated by a script. The logo got a `srcset` too.
5. **Defer heavy setup.** WebGL setup runs in `requestIdleCallback` so the picture paints first; the canvas fades in over an identical image.
6. **Cheaper textures.** The film-grain overlay lost its `mix-blend-mode` (expensive on phones).
7. **Compression when testing.** Our tiny dev server sent files uncompressed, which made Lighthouse pessimistic. Add gzip to any local server you measure with; the real host (Cloudflare) does Brotli.

## Mistakes worth avoiding

- Judging speed from Lighthouse's headline number alone. Also measure real paint times.
- A hidden preview pane or throttled tab makes animations look slow. Time things in a headless Chrome instead (`reference/tools/qa.mjs`).
- A screenshot taken mid crossfade looks like a layout bug. Wait for animations to settle first.

## Accessibility checklist (all met on this site)

- `alt` on every image (empty only for decoration). One `h1` per page and headings in order. (Lighthouse caught our one heading-order slip; fixed with a visually hidden `h2`.)
- A **skip link**, visible focus rings, real buttons and links.
- A hidden UI bar (our sticky mobile buy bar) must not stay focusable: use `visibility: hidden` when off-screen.
- `prefers-reduced-motion`: no intro, no hero movement, no autoplaying film, reveals appear instantly.
- Sound is off until the visitor turns it on; no autoplay audio.
- No element flashes. The Oracle reveal has one brief flash, tinted by the product colour and halved in strength, never a full white flash.
- Contrast: off-white and chartreuse on near-black are far above the minimum. The one thing that slipped: orange text over a bright lava reflection on phones. Fix: a dark gradient behind text that sits on imagery, and check a real phone-size screenshot.
- Structured data (JSON-LD for products and FAQ) is generated only when the site is live.

## Safety net for content

The build has a `draft` and a `live` mode. In `live`, any leftover placeholder text, invented product or missing ingredient list makes the build fail. That protected a food business from publishing invented facts by accident. Consider a similar guard for any site where wrong words could cause harm.
